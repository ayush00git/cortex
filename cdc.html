Content-Defined Chunking, for re-embedding only what changed

A proposal for making document updates cheap in our RAG pipeline. Read top to bottom; the two decisions I need from you are at the very end. Nothing is coded yet.

In one paragraph

Embedding text costs time and money, so when a document changes we want to re-embed only the part that changed, not the whole file. The trouble is that normal "cut every N characters" chunking shifts all the boundaries when you insert text near the top, making everything look new. Content-Defined Chunking (CDC) fixes this by letting the content itself decide where chunks begin and end, so an edit only disturbs the chunks right next to it. Everything else stays byte-for-byte identical and can be reused.

1What problem are we actually solving?

In our pipeline, the slow and costly step is embedding — sending each piece of text to Gemini to get its vector. Reading files and hashing them locally is effectively free; the API call is not.

We already made re-ingestion smarter once: with DocStoreStrategy.UPSERTS_AND_DELETE, re-running ingest skips documents whose contents haven't changed. But that works at the whole-document level — change one line in a document and its entire set of chunks gets re-embedded.

CDC is the next step down: change one line, and we re-embed just the one or two chunks around that line. This proposal is about how to get there.

2Why simple "fixed-size" chunking breaks

Here is the analogy that makes it click (borrowed from the backup world, where CDC was invented):

Imagine splitting a book into chapters of exactly 50 pages each. If someone inserts a single paragraph on page 2, every "chapter" after it shifts by a paragraph — so all of your 50-page boundaries now fall in different places, and the system thinks the whole book is new, even though only one paragraph changed.

That is the boundary-shift problem. Watch it happen with a tiny example. We cut a fixed chunk every 3 words:

Fixed-size chunks — cut every 3 words
before [the cat sat] [on the mat] [and it purred]
after [big the cat] [sat on the] [mat and it] [purred]
Inserting "big" at the front shoved every word over. All chunks differ → all must be re-embedded.

3The CDC idea: let the content choose the cuts

Instead of cutting at fixed positions, CDC slides a small window across the text and computes a rolling hash — a number that depends only on the bytes currently under the window. Whenever that number hits a certain pattern, we declare a cut point right there.

The crucial property: because a boundary is decided by the local content around it, the same content always produces a boundary in the same spot. So after an edit, the boundaries downstream re-synchronise back to where they were before. Same example, but now we cut after any word ending in a specific letter (pretend the rolling hash says "cut after 'sat' and 'mat'"):

Content-defined chunks — cut where content says (• = a cut point)
before the cat sat • on the mat • and it purred
chunks [the cat sat] [on the mat] [and it purred]
after big the cat sat • on the mat • and it purred
chunks [big the cat sat] [on the mat] [and it purred]
Only the first chunk changed. The "sat •" and "mat •" cuts are content-triggered, so they didn't move — those two chunks are identical and get reused (no embedding).

This is exactly the trick that rsync, restic, and borg use to back up a 1 GB file after a one-byte change without re-uploading the whole gigabyte.

4Our one adaptation: chunk the units, not raw bytes

Classic CDC runs the rolling hash over raw bytes, so a cut can land in the middle of a word: "...prioritizes drug tar". That is fine for backups, but terrible for RAG — half a sentence makes a meaningless embedding.

So we apply CDC one level up. First split the text into clean units (lines, sentences, or paragraphs — that's decision Q1 below). Hash each unit down to one number. Then run the rolling hash over that sequence of unit-hashes, and only ever cut between units.

The pipeline
raw text → [ unit₁, unit₂, unit₃, … ] split into clean units
→ [ h₁, h₂, h₃, … ] one hash per unit
→ rolling hash over that list cut only between units
→ chunks = groups of whole units

Result: boundaries are still content-defined (they survive edits), and every chunk is made of whole sentences or lines — clean text the embedder is happy with.

5How the cut is actually decided (the fast version)

We don't need the heavy math from the original Rabin-fingerprint method. The modern approach, FastCDC, uses a tiny, fast rolling hash called a Gear hash:

Gear rolling hash — one step per unit
hash = (hash << 1) + GEAR[ unitHash & 0xFF ] GEAR = fixed table of 256 random numbers
cut here if (hash & mask) == 0 mask sets the average chunk size

Three guard rails keep chunk sizes sane:

  • min size — never cut too soon (avoids a flood of tiny chunks).
  • average size — the target most chunks cluster around, set by the mask.
  • max size — force a cut if we've gone too long (avoids giant chunks).

FastCDC adds one more trick called normalized chunking: use a stricter mask before the target size and a looser one after, which tightens the size distribution. Nice-to-have, not essential for v1.

6The plan: how a re-ingest would work

We keep a small bookkeeping file — a manifest — next to the docstore, listing the chunk hashes we currently have for each file:

./storage/cdc-manifest.json
{ "documents/fory.md": ["a3f9…", "7c21…", "e0b4…"],
  "documents/README.md": ["11ab…", "98fe…"] }

When a file is re-ingested:

  1. Split → CDC → get the new list of chunks, and sha256() each one.
  2. Compare the new hashes against the old ones in the manifest:
    • new hash, not in manifest → embed it, upsert to Qdrant
    • old hash, gone now → delete that vector from Qdrant
    • hash in both → do nothing — reuse the existing vector (free)
  3. Save the new hash list back to the manifest.
Nice side effect

We make the chunk's content hash its ID in Qdrant (as a UUID derived from the sha256). That gives us stable deletes, automatic de-duplication (identical text anywhere = same ID), and a trivial "do we already have this?" check — all for free.

7Honest trade-offs before we build it

Worth weighing

1. The payoff is small on today's files. Our markdown reader already splits each .md into ~30 small section-sized documents, and upsert already re-embeds only the changed sections. CDC's real win shows up with large single documents that change in one spot (big .txt, source code, long PDFs). On small sections, CDC ≈ what we already have.

2. A changed chunk is never free. CDC shrinks the blast radius to the 1–2 chunks around an edit — but those still get re-embedded. It minimizes work, it can't eliminate it.

3. Splitting into units is its own little problem. Naive split(".") trips on e.g., 3.5, and URLs. The unit choice (Q1) directly affects chunk quality.

4. We step off the framework's paved road. Managing IDs and vectors by hand means losing some of LlamaIndex's built-in bookkeeping. Fine for a learning project, but a real divergence.

8What I need you to decide

Q1 — What should a "unit" be?

This is the thing we split into before chunking. It sets how clean the chunk boundaries are.

Lines / blocks my recommendation
Split on newlines and markdown blocks. Zero dependencies, ideal for .md and code-like docs, and edits are already line-localized. Simplest choice that's correct.
Sentences
Better for prose-heavy paragraphs, but needs a sentence splitter that handles abbreviations, decimals, and URLs without breaking.
Paragraphs
Coarsest — fewest chunks, but a one-line edit re-embeds the whole paragraph around it.
